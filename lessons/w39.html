Cloud Deployment: Containers, Serverless & the Edge

⏱️ 50 min🎯 From container to global scale📦 Week 39

By the end of this lesson you'll be able to…

  • Explain what "the cloud" actually rents you — compute, storage, and GPUs you pay for by the minute.
  • Containerise a model with Docker so it runs identically on your laptop and on a server farm.
  • Wrap a model in a tiny web API and reason about autoscaling, serverless, and edge deployment.
  • Name the cloud ML platforms (SageMaker, Vertex AI) and the big ideas — federated learning, AutoML, explainability — they bundle.
  • Talk sensibly about deploying an LLM: inference servers, quantisation, and why cost is the real boss.
The Big Question
Your model runs beautifully on your laptop. A million users show up tomorrow morning. How do you serve every one of them — fast, cheap, and without waking up at 3am to restart a crashed server?

39.1 What the cloud actually rents you

Last week (Week 38, MLOps) we built the discipline of taking a model to production. This week we answer the very physical question: on whose computer does it run? For most teams the answer is the cloud — gigantic data centres owned by AWS, Google Cloud, or Azure that rent you slices of hardware by the second.

Strip away the marketing and the cloud sells you exactly three things:

  • Compute — virtual machines (CPUs) and, crucially for ML, GPUs/TPUs. A deep network that trains for a week on your laptop might train in an hour on eight rented GPUs — then you give them back and stop paying.
  • Storage — somewhere durable to keep terabytes of data and model checkpoints (S3 on AWS, GCS on Google, Blob on Azure). Cheap, near-infinite, accessed over the network.
  • Networking — the glue that lets a user's phone reach your model and lets your services talk to each other.

The killer feature is elasticity: you rent what you need right now and release it the moment you don't. No data centre to build, no GPU to buy for $30,000 that's idle 90% of the time.

🧒 Explain Like I'm 10

Buying a server is like buying a bouncy castle: it's huge, it costs a fortune, and most days it just sits in your garage. The cloud is renting a bouncy castle for the afternoon of the party. If 200 kids show up instead of 20, the rental company just drives over four more. When the party ends, you stop paying. You only ever pay for the fun you're actually having.

39.2 Cloud ML services & databases

You could rent a bare GPU machine and install everything yourself. But the cloud providers also sell managed ML platforms that do the plumbing for you: Amazon SageMaker and Google Vertex AI are the two giants (Azure ML is the third). They bundle a hosted notebook to experiment in, one-click training jobs on rented GPUs, a model registry (the same idea as MLflow from Week 38), and a one-click deploy button that turns a trained model into a live web endpoint with autoscaling already wired up.

Alongside compute, your live app needs databases: a relational store (the SQL from Week 5) for users and orders, and — increasingly — a vector database (Pinecone, pgvector, Weaviate) that stores embeddings and answers "find me the most similar documents" with the cosine-similarity search you met in Week 2. That vector store is the backbone of the RAG chatbot you'll build in Project 5.

🔑 Managed vs. do-it-yourself

Managed platforms (SageMaker/Vertex) trade money and lock-in for speed and fewer 3am pages. Raw VMs + your own Docker trade more setup for full control and portability. There's no universally right answer — but knowing what each layer does lets you choose on purpose.

39.3 Containerisation: Docker

Here is the oldest bug in deployment: "but it works on my machine!" Your laptop has Python 3.11, NumPy 1.26, and a CUDA driver from last March. The server has Python 3.9 and a different CUDA. The model crashes. Docker kills this bug forever by packaging your model together with its entire environment — the exact OS libraries, Python version, and dependencies — into a single sealed unit called an image. Run that image anywhere and you get a container: an identical, isolated copy of your app, byte-for-byte the same on your laptop, a teammate's Mac, and a thousand cloud servers.

You describe the image in a tiny recipe file called a Dockerfile. Each line is a build step, layered on top of the last:

Dockerfile — package the model + its world
# Start from a slim official image that already has Python 3.11
FROM python:3.11-slim

# Everything from here runs inside /app in the container
WORKDIR /app

# Copy ONLY requirements first, so Docker can cache the (slow) pip
# install layer and skip it whenever only our code changes.
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Now copy our code and the trained model file
COPY app.py model.joblib ./

# The container will listen on port 8000
EXPOSE 8000

# The command Docker runs when the container starts:
# launch the FastAPI app with the uvicorn web server.
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]

Two commands turn that recipe into a running service. The first builds the image; the second runs it, mapping the container's port 8000 to your machine's port 8000:

bash — build & run
# Build the image and tag it "iris-api"
docker build -t iris-api .

# Run it; -p maps host:container ports, --rm cleans up on exit
docker run --rm -p 8000:8000 iris-api
# -> now http://localhost:8000/predict is live
📦 Real-World Analogy

Before shipping containers, dockworkers loaded ships by hand — barrels, crates, sacks, all different shapes, all loaded differently in every port. Then someone invented the standard steel container: seal anything inside, and every crane, truck, and ship on Earth handles it identically. Docker is that steel box for software. Your model, its libraries, its quirks — sealed inside one standard unit that every server knows how to lift.

39.4 The serving API + scalability

A model on disk does nothing. To serve it, you wrap it in a small web app that listens for requests, runs the model, and returns the answer as JSON. FastAPI (or Flask) makes this a few lines:

app.py — a tiny predict endpoint
import joblib
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

# Load the trained model ONCE at startup, not on every request.
# (This is the iris Random Forest we registered back in Week 38.)
model = joblib.load("model.joblib")

# Pydantic validates the incoming JSON: 4 floats, the iris features.
class IrisInput(BaseModel):
    features: list[float]   # e.g. [5.1, 3.5, 1.4, 0.2]

@app.post("/predict")
def predict(item: IrisInput):
    # model.predict expects a 2D array (one row), so wrap in a list
    pred = model.predict([item.features])[0]
    return {"prediction": int(pred)}   # -> {"prediction": 0}

# A health check so the cloud's load balancer knows we're alive
@app.get("/health")
def health():
    return {"status": "ok"}

One container serves maybe a few hundred requests per second. A million users need more. Autoscaling is the answer: a load balancer sits in front and spreads requests across many identical containers; an autoscaler watches the load and adds containers when traffic spikes, removes them when it falls. Because every container is a perfect Docker copy, you can spin up the 50th one in seconds. Kubernetes (often via Vertex/SageMaker under the hood) orchestrates this dance.

39.5 Serverless & FaaS

Even autoscaled containers cost money while idle — you still rent the minimum machines that are "always on." Serverless (also called Functions-as-a-Service: AWS Lambda, Google Cloud Functions) pushes elasticity to the extreme: you upload just a function, and the cloud runs it only when a request arrives, billing you per millisecond of execution. Zero traffic, zero cost. It's ideal for spiky, infrequent workloads.

The catch is the cold start: if a function hasn't run recently, the cloud must spin it up from scratch — loading your code and model — adding latency to that first request. For big models the cold start can be seconds, which is why heavyweight LLMs usually live in always-warm containers, while serverless shines for lightweight pre/post-processing.

39.6 Edge computing

Sometimes the cloud is too far away. A self-driving car can't wait 200ms for a round-trip to a data centre to decide whether to brake. Edge computing runs the model on or near the device — the phone, the camera, the car — so inference happens locally with near-zero latency and without shipping private data over the network. The trade-off: edge devices are small, so models must be shrunk (quantised, pruned) to fit. Tools like TensorFlow Lite and ONNX Runtime exist exactly for this.

39.7 Federated learning

Edge raises a beautiful idea: what if we could train without ever collecting users' raw data? Federated learning does just that. Instead of uploading your photos to a server, the model is sent to your phone, trained a little on your local data, and only the resulting weight updates (not the data) are sent back and averaged across millions of devices. Your private data never leaves your hands. This is how phone keyboards learn to predict your next word without Google reading your messages.

39.8 AutoML

Most cloud platforms offer AutoML: hand it a labelled dataset and it automatically searches over models, hyperparameters, and feature transforms to find a strong one — automating the trial-and-error you did by hand in Parts 4 and 5. It's a fast way to get a solid baseline, especially for non-experts, though a thoughtful human still usually beats it on hard, novel problems.

39.9 Explainable AI on the cloud

The SHAP and LIME explainability tools from Week 38 don't disappear in production — the cloud platforms bake them in. SageMaker Clarify and Vertex's Explainable AI attach feature attributions to live predictions and run bias reports as part of the deploy pipeline, so "why did the model decide this?" and "is it fair across groups?" become first-class, monitored outputs rather than afterthoughts.

39.10 Cloud MLOps

Everything from Week 38 — experiment tracking, model registry, CI/CD, drift monitoring — has a managed cloud equivalent (SageMaker Pipelines, Vertex Pipelines). The point of cloud MLOps is to wire the whole loop together: a code change triggers an automated test + retrain, the new model is registered, deployed to a few percent of traffic (a canary), monitored for drift, and either promoted or rolled back — all without anyone manually copying files to a server.

39.11–12 Deploying LLMs: the cost is the catch

Serving the transformers from Part 6 is its own discipline because they are enormous. Three ideas dominate:

  • Inference servers — specialised servers (vLLM, TGI, TensorRT-LLM) that batch many users' requests together, cache the attention keys/values, and stream tokens out one at a time to keep GPUs busy and latency low.
  • Quantisation — storing the model's weights in fewer bits (16-bit, 8-bit, even 4-bit) instead of 32-bit floats. A 4-bit model uses roughly a quarter of the memory and runs faster, with a small, often acceptable, accuracy hit. This is also what makes edge deployment (39.6) feasible.
  • Cost — an LLM might need a GPU costing several dollars per hour, and generation cost scales with the number of tokens. Smart deployment means right-sizing the model (do you need 70B parameters, or will a quantised 7B do?), caching common answers, and batching aggressively.

The rough cost model that haunts every LLM product: total cost \(\approx N_{\text{requests}} \times \big(T_{\text{in}} + T_{\text{out}}\big) \times c_{\text{token}}\), where \(T_{\text{in}}\) and \(T_{\text{out}}\) are input and output tokens and \(c_{\text{token}}\) is the cost per token. Every word the model reads or writes is on the meter.

⚠️ The bill is the boss

A GPU left running overnight by accident can cost more than a developer's daily salary. The most common production mistake isn't a bug — it's forgetting to scale down. Always set autoscaling floors, idle timeouts, and budget alerts before you deploy anything on a GPU.

✅ Check Yourself

What core problem does Docker solve for model deployment?
A Docker image seals the OS libraries, Python version, and dependencies alongside your code and model. The resulting container behaves byte-for-byte the same on a laptop or a thousand cloud servers — accuracy is unchanged, reproducibility is the win.
A self-driving car runs its perception model on a chip inside the car rather than calling a data centre. This is an example of…
Edge computing runs inference on or near the device for near-zero latency and privacy — exactly what a car needs when 200ms of cloud round-trip is too slow to brake safely.
Why is quantisation useful when deploying a large language model?
Quantisation shrinks each weight from 32-bit floats down to 16, 8, or 4 bits. A 4-bit model uses roughly a quarter of the memory and runs faster, usually with an acceptable accuracy hit — and it's what makes edge deployment of big models feasible.
