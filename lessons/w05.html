SQL & Databases: Where Data Lives

⏱️ 50 min🎯 Storing & querying data📦 Week 5

By the end of this lesson you'll be able to…

  • Explain what a database is and why SQL is the universal language for asking it questions.
  • Read a relational schema — tables, rows, columns, primary & foreign keys — and see how relations link data together.
  • Tell the difference between SQL (relational) and NoSQL stores, and pick the right one.
  • Name the five SQL command families (DDL, DML, DQL, TCL, DCL) and write real SELECT, INSERT, UPDATE and DELETE queries.
  • Understand transactions, ACID guarantees, and how databases scale with sharding.
The Big Question
Every model you'll build in this course starts the same way: "give me the data." But where does that data actually live, and how do you ask for exactly the slice you need — out of millions of rows — in a single line?

1. SQL fundamentals: asking a filing cabinet questions

A database is a program whose only job is to store data safely and hand back exactly the part you ask for, fast — even when there are billions of records. SQL (Structured Query Language, say it "sequel" or "S-Q-L") is the language you use to talk to it. You describe what you want; the database figures out how to get it.

🧒 Explain Like I'm 10

A database is a super-organised filing cabinet. Every drawer is a table (say, "Customers"), every folder in the drawer is a row (one customer), and every label on the folder is a column (name, age, city). SQL is the polite way you ask the cabinet: "bring me every folder where the city says Mumbai." You don't open the drawers yourself — you just say what you want, and it appears.

SQL is declarative: you say "I want the names of customers in Mumbai," not "loop over every folder and check the city." That single idea — declare the result, let the engine plan the work — is why one short query can sift millions of rows in milliseconds.

2. RDBMS: tables, rows, keys & relations

The most common kind of database is a relational database (RDBMS) — PostgreSQL, MySQL, SQLite, Oracle. Data lives in tables: a grid of rows (records) and columns (fields). Two ideas make tables powerful:

  • A primary key — a column whose value is unique for every row (like customer_id). It's the folder's barcode: no two folders share it.
  • A foreign key — a column in one table that points at the primary key of another. This is the relation in "relational": it lets an orders table say "this order belongs to customer #42" without copying the customer's whole record.
🔑 The one idea to keep

Don't repeat data — relate it. Store each customer once, then point every order at that one record by its key. This is called normalisation, and it's what keeps a database consistent: change Asha's city in one place and every order "sees" the update.

3. NoSQL: when tables aren't the right shape

Not all data fits neatly into rigid rows and columns. NoSQL ("not only SQL") databases relax the table model for flexibility and scale. The two you'll meet most:

  • Document stores (MongoDB, Firestore): each record is a self-contained JSON-like document. A product can have ten fields, the next product fifteen — no fixed schema. Great when the shape of your data varies or evolves fast.
  • Key–value stores (Redis, DynamoDB): the simplest possible model — a giant dictionary mapping a key to a blob. Blisteringly fast for caches, sessions, and leaderboards.
🗄️ Real-World Analogy

A relational database is a spreadsheet with strict rules: every row must have the same columns, and the accountant won't let you break them. A document store is a shoebox of index cards — each card can say whatever it needs to. The spreadsheet keeps you honest; the shoebox keeps you flexible. Pick based on whether your data is regular (use SQL) or wildly varied and fast-changing (consider NoSQL).

When to use which? Reach for an RDBMS when relationships and consistency matter (banking, orders, anything you'd hate to get wrong). Reach for NoSQL when you need extreme scale, flexible schemas, or simple ultra-fast lookups, and you can tolerate slightly looser guarantees. Most real systems use both.

4. Scaling & sharding

One machine can only hold and serve so much. There are two ways to grow:

  • Vertical scaling ("scale up"): buy a bigger machine — more CPU, RAM, disk. Simple, but there's a ceiling and it gets expensive fast.
  • Horizontal scaling ("scale out"): add more machines and split the data across them. This is where sharding comes in — partitioning rows across servers (e.g. customers A–M on shard 1, N–Z on shard 2). Each shard handles a slice of the traffic.

Replication is the companion idea: keep copies of the data on several machines so reads are fast and a single failure doesn't lose anything. NoSQL systems were largely born to make horizontal scaling and replication easy; traditional RDBMSs can do it too, with more care.

5. The five command families

Every SQL statement belongs to one of five families. Learn the buckets and the whole language organises itself:

We'll use this tiny schema for the rest of the lesson. DDL (Data Definition Language) builds the table itself:

SQL — DDL: define the structure
-- CREATE TABLE defines a new table and its columns + keys (DDL)
CREATE TABLE customers (
    id    INTEGER PRIMARY KEY,   -- unique barcode for each customer
    name  TEXT    NOT NULL,      -- cannot be empty
    city  TEXT,
    spend REAL    DEFAULT 0      -- total amount spent, defaults to 0
);

-- ALTER changes an existing table's shape; DROP would delete it entirely
ALTER TABLE customers ADD COLUMN signup_year INTEGER;

6. DML: changing the data

DML (Data Manipulation Language) puts rows in, edits them, and removes them. Three verbs do almost everything:

SQL — DML: INSERT / UPDATE / DELETE
-- INSERT adds new rows
INSERT INTO customers (id, name, city, spend) VALUES
    (42, 'Asha', 'Mumbai', 1650),
    (43, 'Ravi', 'Delhi',   300),
    (44, 'Meera','Mumbai',  2400);

-- UPDATE edits existing rows. The WHERE clause says WHICH rows.
UPDATE customers SET spend = spend + 100 WHERE id = 43;  -- Ravi spent 100 more

-- DELETE removes rows. ALWAYS pair DELETE with WHERE...
DELETE FROM customers WHERE id = 44;   -- remove just Meera
⚠️ The most expensive missing word in SQL

DELETE FROM customers; with no WHERE deletes every single row. Same trap with UPDATE. Always write the WHERE first, then the verb. Professionals run a SELECT with the same WHERE first to see exactly which rows they're about to touch.

7. DQL: SELECT — the query you'll write 1000 times

DQL (Data Query Language) is just one verb — SELECT — but it's the workhorse of data science. Its clauses run in a fixed logical order: pick the table (FROM), filter rows (WHERE), group them (GROUP BY), filter groups (HAVING), choose columns (SELECT), then sort (ORDER BY) and trim (LIMIT).

SQL — DQL: SELECT
-- The everyday query: which columns, from where, filtered, sorted
SELECT name, spend
FROM   customers
WHERE  city = 'Mumbai'        -- keep only Mumbai customers
ORDER BY spend DESC;          -- biggest spender first
-- -> Meera 2400, Asha 1650

-- Aggregation: one number per group. The heart of analytics.
SELECT city,
       COUNT(*)    AS n_customers,   -- how many per city
       AVG(spend)  AS avg_spend      -- average spend per city
FROM   customers
GROUP BY city
HAVING AVG(spend) > 500;     -- only keep cities averaging over 500

-- JOIN: follow the foreign key to combine tables
SELECT c.name, o.total
FROM   customers c
JOIN   orders    o ON o.cust_id = c.id;   -- relation made visible

That JOIN is the relation from section 2 brought to life: it walks the foreign key and stitches the two tables into one result. COUNT, AVG, SUM, MIN, MAX are aggregate functions — they collapse many rows into a summary. You'll recognise AVG as the mean from Week 4; in Week 8 you'll pull exactly these summaries into Python for EDA.

8. TCL & DCL: transactions, ACID & permissions

Imagine moving ₹500 between two accounts: subtract from one, add to the other. If the power dies between those two steps, money vanishes. TCL (Transaction Control Language) prevents this by wrapping steps into an all-or-nothing transaction.

SQL — TCL & DCL
BEGIN;                                          -- start a transaction
  UPDATE accounts SET bal = bal - 500 WHERE id = 1;
  UPDATE accounts SET bal = bal + 500 WHERE id = 2;
COMMIT;     -- both succeed together; or ROLLBACK to undo BOTH if anything fails

-- DCL: who is allowed to do what
GRANT SELECT ON customers TO analyst;   -- analyst can read, not change
REVOKE SELECT ON customers FROM analyst;

Transactions give you the four ACID guarantees, the reason banks trust SQL databases:

  • Atomicity — all steps happen, or none do (the money transfer above).
  • Consistency — the database moves from one valid state to another; rules (keys, constraints) are never broken.
  • Isolation — concurrent transactions don't trip over each other.
  • Durability — once committed, it survives crashes and power loss.

Finally, DCL (Data Control Language) — GRANT and REVOKE — decides who may read or write each table. The analyst reads; only the app writes. Security by least privilege.

✅ Check Yourself

What is a foreign key?
A foreign key stores the primary-key value of a row in another table — e.g. orders.cust_id = 42 links to customers.id = 42. That link is the "relation" in relational database, and it's what a JOIN follows.
You run DELETE FROM customers; with no WHERE clause. What happens?
With no WHERE, the verb applies to all rows. DELETE wipes the whole table's data (the structure stays). Always write — and test — your WHERE clause first.
The "A" in ACID guarantees that a transaction is atomic. That means:
Atomicity is the all-or-nothing property. In a money transfer, you never end up with the debit applied but the credit lost — either both happen (COMMIT) or neither does (ROLLBACK).
