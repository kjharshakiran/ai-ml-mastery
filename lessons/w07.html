The Big Question
A pure-Python loop over a million numbers is painfully slow, yet ML routinely crunches billions. What's the trick that makes Python fast enough to train neural networks — and how do we write code that doesn't choke on data bigger than memory?

7.2 NumPy & vectorisation: the speed secret

A Python list is flexible but slow for math: each element is a separate boxed object, and a loop pays Python's interpreter overhead on every step. A NumPy array stores numbers in one tight block of memory and runs operations in compiled C — applying them to the whole array at once. That's vectorisation: replace the loop with a single array expression.

Recall the dot product from Week 2, \( \mathbf{a}\cdot\mathbf{b} = \sum_i a_i b_i \). Written as a loop it's slow; written as a @ b it's one fast C call.

python — loop vs vectorised timing
import numpy as np
from time import perf_counter

n = 1_000_000
a = np.random.rand(n)
b = np.random.rand(n)

# --- Slow: a pure-Python loop ---
t0 = perf_counter()
total = 0.0
for i in range(n):
    total += a[i] * b[i]          # interpreter overhead every iteration
loop_time = perf_counter() - t0

# --- Fast: one vectorised expression (same math as Week 2's dot product) ---
t0 = perf_counter()
total_vec = a @ b                 # np.dot under the hood, in compiled C
vec_time = perf_counter() - t0

print(f"loop:       {loop_time:.4f}s")
print(f"vectorised: {vec_time:.6f}s")
print(f"speed-up:   {loop_time / vec_time:.0f}x faster")
# Typical output -> vectorised is ~100-200x faster, and the answers match.
🔑 The rule that will save you years

In numerical Python, if you're writing a for loop over numbers, stop and ask "can NumPy do this on the whole array?" Vectorised code is shorter, clearer, and often 100× faster. This single habit is the difference between code that trains a model in minutes and code that runs overnight.

7.3 & 7.4 Generators & iterators: data without the memory bill

An iterator is anything you can step through one item at a time — that's what a for loop talks to under the hood. A generator is the easy way to build one: a function that uses yield instead of return, producing values lazily, one at a time, only when asked.

Why it matters: a list of a billion numbers needs a billion numbers' worth of RAM. A generator produces them on demand and forgets each one — constant memory, no matter how big the stream.

python — a generator
def read_in_batches(items, size):
    """Yield successive chunks of `items` of length `size`.

    Lazy: holds only one batch in memory at a time, so this works
    even if `items` is a huge file you stream row by row.
    """
    batch = []
    for item in items:
        batch.append(item)
        if len(batch) == size:
            yield batch          # hand back this batch, then PAUSE here
            batch = []           # ...resume here on the next request
    if batch:                    # don't forget a final partial batch
        yield batch

# Consume it lazily — one batch exists at any moment
for chunk in read_in_batches(range(7), size=3):
    print(chunk)
# -> [0, 1, 2]
# -> [3, 4, 5]
# -> [6]
🧒 Explain Like I'm 10

A list is like baking all the cookies before the party — you need a huge tray and a big oven. A generator is a cookie machine that bakes one cookie each time someone asks. You never need a giant tray, and you can keep going forever. yield is the machine handing you the next cookie and then waiting.

7.4 Decorators: wrapping a function in extra behaviour

A decorator is a function that takes another function and returns a souped-up version of it — adding behaviour around the original without touching its code. The classic use is timing or logging.

python — a timing decorator
import functools
from time import perf_counter

def timed(func):
    """Decorator: print how long the wrapped function takes to run."""
    @functools.wraps(func)               # keep func's name & docstring
    def wrapper(*args, **kwargs):
        t0 = perf_counter()
        result = func(*args, **kwargs)   # call the ORIGINAL function
        print(f"{func.__name__} took {perf_counter() - t0:.4f}s")
        return result                    # pass its result straight through
    return wrapper

@timed                                   # <- "wrap slow_sum in timed"
def slow_sum(n):
    return sum(i * i for i in range(n))

slow_sum(1_000_000)
# -> slow_sum took 0.0700s   (the decorator added the timing line for free)

The @timed line is just sugar for slow_sum = timed(slow_sum). You'll see this pattern everywhere in ML frameworks — @property, @staticmethod, and PyTorch's @torch.no_grad() are all decorators.

7.5 Context managers: setup and cleanup, guaranteed

A context manager — the with statement — guarantees that cleanup happens even if an error blows up midway. Opening a file is the everyday example: with makes sure it's closed no matter what.

python — context manager
# The file is automatically closed when the block ends — even on error.
with open("orders.csv", "w") as f:
    f.write("customer,total\n")
    f.write("Asha,165\n")
# <- f.close() happens here, guaranteed. No leaked file handles.

# You'll meet this again as `with torch.no_grad():` in Week 24+,
# which temporarily turns off gradient tracking for fast inference.

7.6 & 7.7 Performance & scaling Python

Putting it together, here's the hierarchy for making Python fast on data:

  1. Vectorise with NumPy/pandas — replace numeric loops with array ops (7.2).
  2. Stream with generators — process data larger than memory in batches (7.3).
  3. Profile, then optimise — use timing (your @timed decorator) to find the real bottleneck before rewriting anything.
  4. Scale out — when one machine isn't enough, tools like Dask or PySpark split the work across cores or machines, echoing the sharding idea from Week 5.
⚠️ Don't optimise blind

"Premature optimisation is the root of all evil." Measure first. Often 95% of the time is in one tiny spot; vectorising that one line beats rewriting the whole program. Reach for the timing decorator before you reach for clever tricks.

✅ Check Yourself

Why is a @ b on NumPy arrays so much faster than a Python for loop doing the same sum?
Vectorisation hands the entire array to compiled C code, so Python's per-iteration interpreter cost is paid once, not a million times. Same math, ~100× faster.
What is the key advantage of a generator (using yield) over building a full list?
A generator is lazy: it yields each value when asked and forgets it, so memory use stays flat regardless of how many items flow through — ideal for data bigger than RAM.
The line @timed above a function definition is shorthand for what?
A decorator replaces the function with decorator(function). @timed is exactly slow_sum = timed(slow_sum), so every call now runs through the timing wrapper.
