The Big Question
You trained a brilliant model in a notebook. Six months from now, with new data flowing in and three teammates touching the code, will it still work — and will you be able to prove it?

38.1 What MLOps is: DevOps for machine learning

For 37 weeks we've built models — regression in Week 13, CNNs in Week 28, transformers in Week 32. Each lived happily inside a notebook. But a notebook is a demo, not a product. The moment a model has to make real decisions for real users, every day, forever, a new discipline kicks in: MLOps — the practices that take a model from "ran once" to "runs reliably."

MLOps borrows from DevOps (the software-engineering culture of automating build, test, and release) and adds the two things that make ML special: data and models are first-class artifacts that change over time. The pillars:

  • Reproducibility — anyone can rebuild your exact result from the same code + data + config. No "magic seed only on my machine."
  • Versioning — not just code (Git), but data and model weights too. The same code on different data is a different model.
  • Pipelines — the path from raw data → features → training → evaluation is automated, not a sequence of cells you remember to run in order.
  • CI/CD — Continuous Integration / Continuous Delivery: every change is automatically tested and, if it passes, shipped.
  • Monitoring — once live, you watch the model's health like a patient, because the world it learned from keeps moving.
🧒 Explain Like I'm 10

Baking one perfect cake at home is easy. Running a bakery is hard: you need the recipe written down (code), the exact same flour every time (data versioning), an oven that bakes 500 cakes a day (deployment), and someone tasting them to make sure they didn't go stale (monitoring). MLOps is the rulebook for turning your one great cake into a bakery that never lets a bad cake out the door.

38.2 A lightweight workflow with MLflow

The very first habit to build is experiment tracking. During Weeks 13–37 you ran dozens of training jobs — different learning rates, different layers, different features. Which one was best? If your answer is "I think it was the one in the cell I overwrote," you've already lost reproducibility.

MLflow is a small open-source tool that fixes this. Two pieces matter:

  • Tracking — every run logs its parameters (hyper-params), metrics (accuracy, loss), and artifacts (the trained model, plots). You get a searchable dashboard of every experiment you've ever run.
  • Model Registry — once a run wins, you register its model under a name and promote it through stages: Staging → Production → Archived. Deployment then just asks the registry for "the current Production model."
mlflow — track an experiment
import mlflow
import mlflow.sklearn
from sklearn.ensemble import RandomForestClassifier
from sklearn.datasets import load_iris
from sklearn.model_selection import train_test_split
from sklearn.metrics import accuracy_score

# 1) Load + split data (the Random Forest from Week 22)
X, y = load_iris(return_X_y=True)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.25, random_state=0)

# 2) Tell MLflow which "experiment" (project) these runs belong to
mlflow.set_experiment("iris-rf")

# 3) Each `with` block is ONE tracked run. Everything inside is logged.
with mlflow.start_run():
    n_estimators, max_depth = 200, 4

    model = RandomForestClassifier(n_estimators=n_estimators,
                                   max_depth=max_depth, random_state=0)
    model.fit(X_tr, y_tr)
    acc = accuracy_score(y_te, model.predict(X_te))

    # Log the knobs we turned (params) and the result (metric)
    mlflow.log_param("n_estimators", n_estimators)   # a hyper-parameter
    mlflow.log_param("max_depth", max_depth)
    mlflow.log_metric("accuracy", acc)               # the score we care about

    # Save the actual trained model as an artifact, and register it by name
    mlflow.sklearn.log_model(model, name="model",
                             registered_model_name="iris-classifier")

    print(f"logged run with accuracy = {acc:.3f}")
    # -> logged run with accuracy = 0.974
# Run `mlflow ui` in a terminal to browse every run in a web dashboard.
🔑 The one habit to keep

If a result isn't logged, it didn't happen. Track params, metrics, and the model artifact on every run from day one. Future-you (and your teammates) will be able to answer "why did we ship this version?" instead of guessing.

38.3 The tool landscape

No single tool does everything; MLOps is a stack you assemble. The essentials, mapped to the problem each one solves:

  • MLflow — experiment tracking + model registry (section 38.2).
  • DVC (Data Version Control) — "Git for data." It versions large datasets and model files that are too big for Git, while keeping a tiny pointer in Git so code and data stay in sync.
  • Docker — packages your model plus its exact environment (Python version, libraries) into a container that runs identically everywhere. (This is Week 39's main act.)
  • Kubeflow — runs ML pipelines on Kubernetes at scale, orchestrating multi-step training/serving workflows across many machines.
  • Airflow / Prefect — schedule and orchestrate the pipeline (e.g. "retrain every Monday at 2am").
  • Evidently / WhyLabs — monitoring dashboards that detect drift (section 38.4).
🏭 Real-World Analogy

Think of a factory assembly line. DVC is the warehouse logging which batch of raw materials went into each product. MLflow is the quality-control clipboard recording every test result. Docker is the shipping crate that protects the product in transit. Kubeflow is the conveyor-belt system tying it all together. You don't buy one machine — you design a line.

38.4 The challenges: drift, skew, and monitoring

Here's the uncomfortable truth that separates ML from ordinary software: your model can rot while the code never changes. A web server behaves the same on Tuesday as on Monday. A model's accuracy can quietly collapse, because the world it learned from has moved on. Three distinct failures:

  • Data drift — the input distribution \(P(X)\) shifts. A spam filter trained in 2023 meets 2026's new phishing styles; the features look different from training.
  • Concept drift — the relationship \(P(y \mid X)\) itself changes. The same input now means something different — e.g. "free shipping" was once a spam signal, now every legit shop says it.
  • Training–serving skew — the features computed at training time differ subtly from those computed live at serving time (different code paths, a missing normalisation). The model sees inputs it was never trained on, despite no drift at all.

We detect drift by comparing distributions. A common test is the Population Stability Index, which sums how much each bucket of a feature shifted between a reference window and live traffic:

\[ \text{PSI} = \sum_{i} \left( p_i^{\text{live}} - p_i^{\text{ref}} \right) \ln\!\frac{p_i^{\text{live}}}{p_i^{\text{ref}}} \]

A PSI above ~0.2 is a loud alarm that the inputs have moved. The fix is monitoring: log live predictions and (when ground truth eventually arrives) live accuracy, alert on drops, and trigger a retrain — which closes the loop back to "Data" in our diagram.

Population Stability Index, by hand

The sum is abstract until you bucket a real feature. Say a feature falls into low/med/high bins. At training time the split was 50/30/20%; live traffic now reads 30/30/40%. Compute each term \((p^{\text{live}} - p^{\text{ref}})\ln\frac{p^{\text{live}}}{p^{\text{ref}}}\).

Bucketreflive\((p^{\text{live}}-p^{\text{ref}})\ln\frac{p^{\text{live}}}{p^{\text{ref}}}\)
low0.500.30\((-0.2)\ln(0.6) = +0.102\)
med0.300.30\(0 \times \ln(1) = 0\)
high0.200.40\((+0.2)\ln(2.0) = +0.139\)

Step 1 — sum the buckets. Add the three terms: \(0.102 + 0 + 0.139 = 0.24\).

\[ \text{PSI} = 0.102 + 0 + 0.139 = 0.24 \]

Step 2 — read the verdict. \(0.24\) sits above the \(\sim0.2\) alarm line, so this feature has drifted enough to justify a retrain. Had the live distribution exactly matched the reference, every \(\ln(1)=0\) and the PSI would be \(0\).

🔑 PSI only ever grows

Each term \((p^{\text{live}}-p^{\text{ref}})\ln\frac{p^{\text{live}}}{p^{\text{ref}}}\) is \(\ge 0\) — when a bucket grows, both factors are positive; when it shrinks, both are negative; the product is positive either way. So PSI rises monotonically as distributions diverge: \(\sim0.1\) is a minor shift to watch, \(\sim0.2\) is a signal to act.

⚠️ The silent failure

Training–serving skew throws no error. Accuracy just quietly sags. The classic culprit: you log-transform a feature in your training notebook but forget to apply the exact same transform in the serving API. The cure is to share a single preprocessing function (or pipeline) between training and serving — never two copies that can drift apart.

38.5 Responsible & Explainable AI

Shipping a model means it now affects people — who gets a loan, a diagnosis, a job interview. That makes Responsible AI not optional. Two threads:

Fairness & bias. A model trained on historical data inherits historical bias. If past hiring favoured one group, a model that learns to predict "would we have hired them?" will too. We measure this with fairness metrics — e.g. demographic parity (the positive-prediction rate should be similar across groups) or equalised odds (similar true-positive and false-positive rates across groups) — and we mitigate by reweighting data, adjusting thresholds, or constraining training.

Transparency & explainability. A 175-billion-parameter model is a black box. Explainable AI (XAI) opens it just enough to ask "why did you predict that?" Two famous tools:

  • LIME (Local Interpretable Model-agnostic Explanations) — to explain one prediction, it wiggles the input slightly, watches how the output changes, and fits a tiny linear model in that neighbourhood. The linear weights tell you which features pushed this one decision.
  • SHAP (SHapley Additive exPlanations) — borrows the Shapley value from game theory: it fairly distributes the prediction among the features by averaging each feature's marginal contribution over all possible orderings. SHAP values are additive and sum back to the prediction, giving consistent, theoretically grounded attributions.
🧒 Explain Like I'm 10

Imagine a robot says "loan denied" and you ask "why?" SHAP is like the robot honestly splitting the blame: "low income took away 30 points, short credit history took away 10, but living in the city added 5." Now you know what mattered — and you can check it wasn't something unfair, like a zip code standing in for race.

✅ Check Yourself

A model's accuracy quietly drops over months even though no one changed the code. What's the most likely cause?
Unlike ordinary software, an ML model decays as the world moves. Data drift (inputs shift) or concept drift (the input→output relationship shifts) erode accuracy without any code change — which is why monitoring and retraining loops exist.
In MLflow, what is the Model Registry for?
Tracking logs each run; the Registry manages the winning models — giving each a name, version, and lifecycle stage so deployment can simply request "the current Production model."
SHAP and LIME both aim to do what?
Both are explainability (XAI) tools. LIME fits a local linear surrogate around one prediction; SHAP uses game-theoretic Shapley values to fairly split a prediction among its features. Both turn a black box into something you can interrogate for correctness and fairness.
