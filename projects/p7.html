7.1 Recap: rebuild the modeling dataset

Picking up exactly where Project 6 left off. Paste Project 6's generator if you're running this page fresh — here's the condensed version, with one upgrade: the provider-rejection-rate feature is now fit on train only, closing the leakage gap Project 6 flagged.

python — rebuild df, train, test (see Project 6 for full derivation)
import numpy as np, pandas as pd
rng = np.random.default_rng(7)
N_PAT, N_VIS = 600, 3000
cities=["Hyderabad","Pune","Bangalore","Mumbai","Delhi","Chennai"]
insurers=["MediCareX","CareOne","HealthPlus","SecureLife"]
depts=["General","ER","Neurology","Orthopedics","Cardiology","ICU"]; vtypes=["ER","OPD","ICU"]
start,end=pd.Timestamp("2025-01-01"),pd.Timestamp("2026-01-01")
rd=lambda n: start+pd.to_timedelta(rng.integers(0,(end-start).days,n),unit="D")
patients=pd.DataFrame({"patient_id":range(1,N_PAT+1),"age":rng.integers(1,90,N_PAT),
  "gender":rng.choice(["M","F"],N_PAT),"city":rng.choice(cities,N_PAT),
  "insurance_provider":rng.choice(insurers,N_PAT),"chronic_flag":rng.integers(0,2,N_PAT),
  "registration_date":rd(N_PAT)})
visits=pd.DataFrame({"visit_id":range(1,N_VIS+1),"patient_id":rng.choice(patients.patient_id,N_VIS),
  "visit_date":np.sort(rd(N_VIS)),"department":rng.choice(depts,N_VIS),
  "visit_type":rng.choice(vtypes,N_VIS),
  "length_of_stay_hours":np.round(rng.gamma(4,5,N_VIS),1),"doctor_id":rng.integers(1,40,N_VIS)})
j=visits.merge(patients,on="patient_id")
risk_logit=0.01*(j.age-45)+0.3*j.chronic_flag+rng.normal(0,1.5,N_VIS)
visits["risk_score"]=pd.cut(risk_logit,bins=[-np.inf,-0.3,0.6,np.inf],labels=["Low","Medium","High"])
billing=pd.DataFrame({"bill_id":range(1,N_VIS+1),"visit_id":visits.visit_id,
  "billed_amount":np.round(rng.gamma(6,3500,N_VIS),2)})
rej_p=0.15+rng.normal(0,0.01,N_VIS); u=rng.random(N_VIS)
billing["claim_status"]=np.where(u<rej_p,"Rejected",np.where(u<rej_p+0.25,"Pending","Paid"))
billing["approved_amount"]=np.where(billing.claim_status=="Rejected",np.nan,
  billing.billed_amount*rng.uniform(0.7,1.0,N_VIS))
billing["payment_days"]=np.where(billing.claim_status=="Paid",rng.integers(3,30,N_VIS).astype(float),np.nan)

df=visits.merge(patients,on="patient_id").merge(billing,on="visit_id").sort_values("visit_date").reset_index(drop=True)
df["los_winsorized"]=df.length_of_stay_hours.clip(upper=df.length_of_stay_hours.quantile(0.99))
df["days_since_registration"]=(df.visit_date-df.registration_date).dt.days   # left UNCLIPPED on purpose -- see 7.6
df["visit_month"]=df.visit_date.dt.month; df["visit_quarter"]=df.visit_date.dt.quarter
df["visit_dayofweek"]=df.visit_date.dt.dayofweek; df["is_weekend_visit"]=(df.visit_dayofweek>=5).astype(int)

split=int(len(df)*0.8); train,test=df.iloc[:split].copy(),df.iloc[split:].copy()

# Patient + provider aggregates fit on TRAIN ONLY, then mapped onto test --
# this is the leakage fix Project 6 section 6.7 promised.
agg=train.groupby("patient_id").agg(patient_visit_freq=("visit_id","count"),
                                     patient_avg_los=("length_of_stay_hours","mean"))
rej=train.groupby("insurance_provider").claim_status.apply(lambda x:(x=="Rejected").mean()).rename("provider_rejection_rate")
for part in (train,test):
    part[["patient_visit_freq","patient_avg_los"]]=part.patient_id.map(agg.patient_visit_freq).to_frame().assign(
        patient_avg_los=part.patient_id.map(agg.patient_avg_los))
    part["provider_rejection_rate"]=part.insurance_provider.map(rej)
print(len(train), len(test))

7.2 Choosing a model: the bias-variance conversation

Three contenders, same conversation a production ML team has every time:

  • Logistic Regression (Week 13/25) — a straight-line decision boundary per class. Fast, interpretable, the baseline you compare everything else against.
  • Random Forest (Week 22) — a committee of decision trees, each trained on a different random slice of rows and columns, voting together. Captures non-linear interactions a linear model can't.
  • Gradient Boosting (Week 22) — trees built sequentially, each one fixing the previous tree's mistakes. Usually the strongest off-the-shelf tabular performer, at the cost of being slower to train and easier to overfit if left unchecked.

We'll use Random Forest for risk_score and Gradient Boosting for claim_status — not because one is universally better, but because this is exactly what the real production system did, and comparing their two different failure modes is the whole point of section 7.4.

🌳 Real-World Analogy

Random Forest is a room of independent doctors who each only saw part of the patient's chart, voting on a diagnosis — their independence cancels out individual blind spots. Gradient Boosting is one resident who keeps re-examining the patient, each pass specifically hunting for what the last pass got wrong. Both can be excellent; they fail differently, which is why section 7.4 evaluates them differently too.

7.3 Train both models

python — Random Forest for risk_score
from sklearn.pipeline import Pipeline
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import accuracy_score, f1_score, classification_report

RISK_FEATURES = ["age","gender","city","insurance_provider","chronic_flag",
                  "days_since_registration","patient_visit_freq","patient_avg_los",
                  "department","visit_type","visit_month","visit_quarter",
                  "visit_dayofweek","is_weekend_visit"]

cat = [f for f in RISK_FEATURES if not pd.api.types.is_numeric_dtype(df[f])]
num = [f for f in RISK_FEATURES if pd.api.types.is_numeric_dtype(df[f])]
pre = ColumnTransformer([("ohe", OneHotEncoder(handle_unknown="ignore"), cat),
                          ("sc",  StandardScaler(), num)])
risk_model = Pipeline([("pre", pre), ("clf", RandomForestClassifier(
    n_estimators=200, min_samples_leaf=5, class_weight="balanced_subsample",
    random_state=42))])
risk_model.fit(train[RISK_FEATURES], train.risk_score)

train_acc = accuracy_score(train.risk_score, risk_model.predict(train[RISK_FEATURES]))
test_acc  = accuracy_score(test.risk_score,  risk_model.predict(test[RISK_FEATURES]))
print(f"train accuracy: {train_acc:.3f}   test accuracy: {test_acc:.3f}")
# At this 3,000-row demo scale: train ~0.89, test ~0.44.
# At the real project's 25,000-row production scale, the SAME model
# architecture scored train 0.985, test 0.394 -- an even bigger gap.
# Either way: textbook overfitting. Keep reading -- this is the point.
⚠️ 98.5% train accuracy is not good news

A model that nails the training set but falls apart on data it hasn't seen has memorized, not learned. In the real production run, High-Risk recall on the test set was just 8.8% — the model missed 91% of the genuinely high-risk visits. A flashy training-accuracy number with no test-set discipline is how unsafe models ship. Always report both, always be suspicious of a huge gap between them.

python — Gradient Boosting for claim_status
from sklearn.ensemble import GradientBoostingClassifier

CLAIM_FEATURES = ["age","gender","city","insurance_provider","chronic_flag",
                   "department","visit_type","los_winsorized","risk_score",
                   "visit_month","visit_quarter","is_weekend_visit","billed_amount",
                   "provider_rejection_rate","patient_visit_freq","days_since_registration"]
catc = [f for f in CLAIM_FEATURES if not pd.api.types.is_numeric_dtype(df[f])]
numc = [f for f in CLAIM_FEATURES if pd.api.types.is_numeric_dtype(df[f])]
prec = ColumnTransformer([("ohe", OneHotEncoder(handle_unknown="ignore"), catc),
                           ("sc",  StandardScaler(), numc)])
claim_model = Pipeline([("pre", prec), ("clf", GradientBoostingClassifier(
    n_estimators=150, max_depth=4, subsample=0.8, random_state=42))])
claim_model.fit(train[CLAIM_FEATURES], train.claim_status)
preds = claim_model.predict(test[CLAIM_FEATURES])
print(classification_report(test.claim_status, preds, digits=3))
# The model leans hard on "Paid" (high recall there) and is weak on
# Pending/Rejected -- the two classes a revenue team actually needs
# flagged. In the real project, Rejected recall was 15.0%.

7.4 Evaluate honestly: the business metric, not just accuracy

"Accuracy" treats every mistake equally. A hospital does not: missing a genuinely High-Risk visit is a different kind of mistake than mislabeling a Low as Medium. So the real evaluation report leads with per-class recall on the class that matters, not the headline accuracy number:

\[ \text{recall(High)} = \frac{\text{visits correctly flagged High}}{\text{all visits that were actually High}} \]

python — the recall numbers that actually matter
rep = classification_report(test.risk_score, risk_model.predict(test[RISK_FEATURES]), output_dict=True)
print("High-Risk recall:", round(rep["High"]["recall"], 3))

# Fairness: is recall even across patient groups, or does the model
# quietly work better for some groups than others?
def group_recall(target, preds, truth, group_col, frame):
    out = {}
    for g in frame.loc[truth.index, group_col].unique():
        idx = frame.loc[truth.index, group_col] == g
        t, p = truth[idx], preds[idx]
        if (t == target).sum() == 0: continue
        out[g] = round(float(((p == target) & (t == target)).sum() / (t == target).sum()), 3)
    return out

preds = risk_model.predict(test[RISK_FEATURES])
print("High-Risk recall by city:", group_recall("High", preds, test.risk_score, "city", df))
# Real production result: city recall ranged from 3.0% (Mumbai) to
# 14.1% (Pune) -- a >10-point spread the team flagged for review.
# Given every group's recall was already low, this read as "the model
# isn't finding real signal anywhere" rather than "biased toward one city" --
# but you only know that because you checked.
🔑 A fairness gap needs a second opinion before you act on it

A wide spread across groups is always worth flagging — but the right response depends on context. If every group's recall is reasonably high except one, that's a targeted bias to fix. If every group's recall is poor (as here), the honest read is "this model isn't predictive enough to deploy," not "rebalance the training data." Don't skip straight to a fix without first asking which story the numbers are actually telling.

7.5 Building the API: validate at the boundary

A model is not a product. A product is something a hospital's other systems can call, with guarantees. FastAPI + Pydantic give you those guarantees for free: every request is checked against a schema before it ever reaches the model.

api.py — request schema with hard guarantees
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field, field_validator

app = FastAPI(title="Hospital Risk Intelligence API", version="1.0.0")

class RiskRequest(BaseModel):
    age: int = Field(..., ge=1, le=120)          # reject impossible ages outright
    gender: str
    visit_type: str
    days_since_registration: int = Field(..., ge=0)
    patient_avg_los: float = Field(..., ge=0)
    # ... remaining RISK_FEATURES fields, same pattern

    @field_validator("visit_type")
    @classmethod
    def check_visit_type(cls, v):
        if v not in ["OPD", "ER", "ICU"]:
            raise ValueError("visit_type must be OPD, ER, or ICU")
        return v

@app.get("/health")
def health():
    return {"status": "healthy", "model_version": "1.0.0"}

@app.post("/predict/risk")
def predict_risk(req: RiskRequest):
    data = req.model_dump()
    pred = risk_model.predict([list(data.values())])[0]   # simplified for illustration
    return {"prediction": pred, "model_version": "1.0.0"}
# A request with age=-5 or visit_type="Surgery" never reaches risk_model
# at all -- it's rejected with HTTP 422 and a field-by-field error list,
# before a single line of model code runs. That boundary is the whole job.
🧒 Explain Like I'm 10

Think of the API schema as a bouncer at a club door with a checklist: "Are you over 1 and under 120 years old? Is your visit type one of the three we allow?" Anyone who fails the checklist never gets inside to bother the model. The model only ever sees clean, sane requests — which is exactly why it can keep being simple on the inside.

7.6 Logging every prediction — without logging the patient

When something goes wrong three weeks from now, you need to answer "what did we predict, when, with which model version, for what input?" — without storing anything that identifies the patient. The trick: hash the input instead of storing it.

python — audit logging via a feature hash, not raw data
import hashlib, json
from datetime import datetime

def log_prediction(payload: dict, prediction: str, model_version: str):
    feature_hash = hashlib.md5(json.dumps(payload, sort_keys=True).encode()).hexdigest()
    record = {
        "prediction_id": feature_hash[:8],
        "input_feature_hash": feature_hash,     # reproducible, but not reversible to PII
        "timestamp": datetime.utcnow().isoformat() + "Z",
        "model_version": model_version,
        "prediction": prediction,
    }
    print(record)   # in production: append as one JSON line to a log file/stream
    return record

log_prediction({"age": 58, "visit_type": "ER"}, "Low", "1.0.0")

7.7 Monitoring in production: did the world change under the model?

A model trained on January's patients can quietly stop being valid by June, even with zero code changes — the input distribution shifted. The Population Stability Index (PSI) measures exactly that, by comparing how a feature's values are distributed now versus when the model was trained:

\[ \text{PSI} = \sum_i (\text{curr}_i - \text{ref}_i) \times \ln\!\left(\frac{\text{curr}_i}{\text{ref}_i}\right) \]

where \(i\) ranges over value bins. PSI < 0.10 is stable, 0.10–0.20 deserves a closer look, > 0.20 typically triggers a retrain.

python — PSI drift check, reusing train vs test as reference vs current
def psi(ref, curr, bins=10):
    b = np.linspace(min(ref.min(), curr.min()), max(ref.max(), curr.max()), bins+1)
    b[0] -= 1e-6; b[-1] += 1e-6
    rp = (pd.cut(ref, bins=b).value_counts(sort=False) / len(ref)).clip(lower=1e-6)
    cp = (pd.cut(curr, bins=b).value_counts(sort=False) / len(curr)).clip(lower=1e-6)
    return float(((cp - rp) * np.log(cp / rp)).sum())

score = psi(train.days_since_registration, test.days_since_registration)
print(f"PSI(days_since_registration) = {score:.2f}")
print("ref mean:", round(train.days_since_registration.mean(),1),
      " curr mean:", round(test.days_since_registration.mean(),1))
# At demo scale: PSI ~5.5, ref mean ~ -36, curr mean ~ +144.
# In the real project: PSI 4.38, ref mean -33.2, curr mean +147.7.
# Both numbers are enormous -- and BOTH are the same false alarm.
⚠️ The monitor just re-found Project 6's bug — read the alert, don't just act on it

A negative mean for "days since registration" is impossible in reality — exactly the registration-date bug Project 6 section 6.5 flagged, because days_since_registration was deliberately left unclipped. The chronological split makes it worse: early rows draw a registration date from the whole year (often after the visit, pushing the mean negative); late rows draw from a range now mostly before the visit (pushing the mean positive). A naive on-call engineer sees PSI 4+ and triggers an expensive retrain. The right response — proven by tracing it back to section 6.5 — is to .clip(lower=0) the feature and re-check, not to retrain a model that was never the problem. This is why monitoring and EDA have to talk to each other.

✅ Check Yourself

Train accuracy 98.5%, test accuracy 39.4%. What's the right read?
A ~60-point gap between train and test accuracy is the signature of overfitting. The model is not learning a generalizable pattern — it memorized training noise. Test performance, not train, is what production will actually see.
A drift monitor flags PSI = 4.38 on a feature whose reference-period mean is negative, which is logically impossible. What should you do first?
PSI tells you a distribution changed, not why. A logically impossible value (negative tenure) is a strong clue the "drift" is an artifact of how the feature was built, not a real shift in the world — exactly what section 7.7 traces back to Project 6's EDA finding.
Why does the API log an input_feature_hash instead of the raw request?
A hash is reproducible (the same input always hashes the same way) but not reversible (you can't recover the input from the hash) — exactly the property you want for an audit trail that respects privacy.
