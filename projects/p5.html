Ship It — Deploy a Model + RAG Chatbot to the Cloud

🟡 Difficulty: Intermediate🎯 From notebook to product🧰 FastAPI · RAG · Embeddings · Docker · MLOps

What you'll build

  • A FastAPI service that wraps a model behind a clean HTTP endpoint.
  • A working RAG pipeline: chunk docs → embed → store vectors → retrieve by cosine similarity → stuff into a prompt.
  • A retrieve() built from scratch on NumPy cosine similarity — the dot product of Week 2, in production.
  • A Dockerfile that containerises the whole thing into one reproducible image.
  • A concrete plan for cloud deployment, scaling, and monitoring (MLOps).
The Big Question
A trained model sitting in a notebook helps no one. How do you turn it into a service the world can call — and how do you give an LLM access to your private documents without retraining it?

The previous four projects built models. This one ships one. We'll also solve the single most common real-world LLM problem: the model knows the internet but not your company handbook. The answer is RAG — Retrieval-Augmented Generation (Week 34): instead of retraining, we look up the relevant passages and hand them to the model as context.

🧒 Explain Like I'm 10

Imagine a super-smart friend who has read most books but has never seen your school's rulebook. Instead of making them re-read everything, you let them keep the rulebook open and say "answer using these pages." That's RAG: when you ask a question, the computer quickly finds the most relevant pages from your documents and slips them to the AI before it answers. "Deploying" is just putting your smart friend behind a doorbell (an API) so anyone can ring and ask a question.

The serving + RAG architecture

Step 1 — Index documents: chunk & embed

We split documents into bite-sized chunks and turn each into a dense vector with a pretrained sentence-transformer — the exact "swap TF-IDF for embeddings" upgrade from Project 2, and the same "reuse a frozen pretrained model" pattern from Project 3.

step1_index.py
import numpy as np
from sentence_transformers import SentenceTransformer

# A small, fast, pretrained embedding model (384-dim vectors).
embedder = SentenceTransformer("all-MiniLM-L6-v2")

# In reality you'd load & split real files; here are a few "knowledge" chunks.
docs = [
    "Our refund policy allows returns within 30 days of purchase.",
    "Standard shipping takes 3-5 business days within the country.",
    "Premium members get free express shipping and priority support.",
    "To reset your password, click 'Forgot password' on the login page.",
]

# Embed every chunk once, offline. Normalise so cosine == dot product.
doc_vecs = embedder.encode(docs, normalize_embeddings=True)  # (4, 384)
doc_vecs = np.asarray(doc_vecs, dtype=np.float32)
print("indexed", doc_vecs.shape[0], "chunks of dim", doc_vecs.shape[1])

Step 2 — Retrieve with NumPy cosine similarity (Week 2!)

The "vector database" is, at its core, this one function. Cosine similarity is the dot product of unit vectors — the very first similarity measure from Week 2, now deciding which passages an LLM gets to read:

\[ \cos\theta = \frac{\mathbf{q}\cdot\mathbf{d}}{\lVert\mathbf{q}\rVert\,\lVert\mathbf{d}\rVert} \]

step2_retrieve.py
def retrieve(query, k=2):
    # Embed the query the SAME way we embedded the docs.
    q = embedder.encode([query], normalize_embeddings=True)[0]  # (384,)
    q = np.asarray(q, dtype=np.float32)

    # Because both q and doc_vecs are unit-normalised, the dot product
    # IS the cosine similarity. One matrix-vector multiply ranks every chunk.
    scores = doc_vecs @ q                       # (n_docs,) similarity to query

    # Take the indices of the k highest-scoring chunks.
    top = np.argsort(scores)[::-1][:k]
    return [(docs[i], float(scores[i])) for i in top]

for chunk, score in retrieve("how long do I have to send something back?"):
    print(f"{score:.3f}  {chunk}")
# -> the refund-policy chunk ranks first, even though the wording differs.
# That semantic match is why embeddings beat keyword search.
🔑 A vector DB is just this, at scale

Pinecone, FAISS, Chroma and friends do exactly what retrieve() does — embed, then rank by cosine similarity — but with clever indexes (HNSW, IVF) so it stays fast across millions of vectors. The idea never changes: the dot product from Week 2 is the retrieval engine of every RAG system on earth.

Step 3 — Assemble the prompt & call the LLM

RAG's final move: stuff the retrieved chunks into the prompt as context, instruct the model to answer only from them, and generate. This grounds the answer in your data and slashes hallucination.

step3_rag.py
def build_prompt(query):
    chunks = retrieve(query, k=2)
    context = "\n".join(f"- {c}" for c, _ in chunks)
    return (
        "Answer the question using ONLY the context below. "
        "If the answer isn't there, say you don't know.\n\n"
        f"Context:\n{context}\n\nQuestion: {query}\nAnswer:"
    )

def answer(query):
    prompt = build_prompt(query)

Step 4 — Wrap it in a FastAPI endpoint

FastAPI turns a Python function into a typed HTTP service in a few lines. Run it with uvicorn app:app and you have a real API with automatic docs at /docs.

app.py
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI(title="RAG Chatbot")

class Query(BaseModel):
    question: str            # request schema -> auto-validated & documented

@app.get("/health")          # liveness probe for the cloud load balancer
def health():
    return {"status": "ok"}

@app.post("/ask")
def ask(q: Query):
    chunks = retrieve(q.question, k=2)
    return {
        "answer": answer(q.question),
        "sources": [c for c, _ in chunks],   # show provenance -> trust
    }
# Run locally:  uvicorn app:app --host 0.0.0.0 --port 8000
# Then POST {"question": "..."} to http://localhost:8000/ask

Step 5 — Containerise with Docker

A container freezes your code, dependencies and runtime into one image that runs identically on your laptop and in the cloud (Week 39). "Works on my machine" becomes "works everywhere."

Dockerfile
# Small, pinned base image for reproducibility.
FROM python:3.11-slim

WORKDIR /app

# Install deps first so Docker can cache this layer between code changes.
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy the app (and the prebuilt vector index).
COPY . .

EXPOSE 8000
# Production server: uvicorn workers behind the container's port.
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
📦 Real-World Analogy

A Docker image is a shipping container for software. A ship doesn't care whether it's carrying bananas or bicycles — the container is a standard box that fits any crane, any port, any vessel. Likewise the cloud doesn't care what's inside your image; it just runs the box. That standardisation is what makes "deploy anywhere" possible.

Step 6 — Deploy & monitor (MLOps, Week 38)

Shipping isn't done at deploy — it's done when you can watch it. The MLOps checklist (Week 38) that turns a container into a reliable product:

  • Build & push: docker build -t rag-bot ., push to a registry (ECR/GCR/Docker Hub).
  • Run it: a managed container service (Cloud Run, ECS, or Kubernetes) pulls the image and exposes the API behind autoscaling + HTTPS.
  • Health checks: the platform pings /health and restarts unhealthy instances automatically.
  • Monitor: log latency, error rate, and tokens/request; alert on spikes. Track answer quality and watch for data drift (questions changing over time).
  • Iterate safely: version the model and the vector index; roll out behind a canary so a bad release hits 5% of traffic, not 100%.

🚀 Make it your own

  • Use a real vector DB. Swap the NumPy retrieve() for FAISS or Chroma and index thousands of your own documents.
  • Add citations in the answer. Have the LLM cite which chunk each claim came from for full traceability.
  • Stream the response. Return tokens as they generate with FastAPI's StreamingResponse for a snappy chat feel.
  • Add a rerank stage. Retrieve 20 chunks by cosine, then use a cross-encoder to rerank the top 5 for sharper context.
  • Wire up observability. Add Prometheus metrics and a dashboard for latency, request volume, and retrieval scores.
