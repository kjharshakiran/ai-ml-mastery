8.1 The brief

A private aviation operator wants two predictions made the moment a reservation is booked and billed:

  • Flight outcome risk (flight_outcome: Completed / No-Show / Cancelled) — so operations can right-size crew and fuel planning, and flag high-cancellation bookings for a confirmation call.
  • Invoice outcome (payment_status: Paid / Pending / Disputed) — so finance can chase the invoices most likely to be disputed, before the dispute happens.

Notice this is structurally identical to Project 6's brief. That's not a coincidence — it's the point. The vast majority of "build me a model" requests inside any company reduce to this same shape: predict an operational outcome, predict a revenue outcome, from a handful of related tables.

8.3 SQL first

python — load tables into SQL, then ask the business questions
import sqlite3, pandas as pd
conn = sqlite3.connect(":memory:")
customers.to_sql("customers", conn, index=False)        # built in section 8.4 below
reservations.to_sql("reservations", conn, index=False)
billing.to_sql("billing", conn, index=False)

# Q1: which aircraft type flies most, and what's the average invoice?
print(pd.read_sql("""
SELECT aircraft_type, COUNT(*) AS n_flights, ROUND(AVG(b.invoice_amount),2) AS avg_invoice
FROM reservations r JOIN billing b ON r.reservation_id=b.reservation_id
GROUP BY aircraft_type ORDER BY n_flights DESC;
""", conn))

# Q2: which aircraft type disputes the most invoices?
print(pd.read_sql("""
SELECT aircraft_type,
  ROUND(100.0*SUM(CASE WHEN payment_status='Disputed' THEN 1 ELSE 0 END)/COUNT(*),1) AS disputed_pct
FROM reservations r JOIN billing b ON r.reservation_id=b.reservation_id
GROUP BY aircraft_type ORDER BY disputed_pct DESC;
"""))
# Typical output: dispute rate ranges roughly 10-15% across aircraft
# types -- close enough that "aircraft type alone" won't be a strong
# predictor by itself, same conclusion Project 6 reached for insurers.
🔑 The pattern transfers, the numbers don't have to

Project 6 found insurers reject within a few points of each other (~15% each). Here, aircraft types dispute within a few points of each other too (~10-15%). The specific percentages are coincidental to how we seeded the simulation — the reasoning move ("check if the group-level rates are actually different before trusting a categorical feature to carry the signal") is what transfers, and it transfers to literally any domain with a categorical breakdown and an outcome rate.

Top customers and the monthly revenue trend — the same JOIN + GROUP BY + date-bucket pattern as Project 6 section 6.3:

sql — top customers by spend, revenue by month
print(pd.read_sql("""
SELECT c.customer_id, COUNT(*) AS n_flights, ROUND(SUM(b.invoice_amount),2) AS total_spend
FROM reservations r JOIN billing b ON r.reservation_id=b.reservation_id
              JOIN customers c ON r.customer_id=c.customer_id
GROUP BY c.customer_id ORDER BY total_spend DESC LIMIT 5;
""", conn))

print(pd.read_sql("""
SELECT strftime('%Y-%m', flight_date) AS month, COUNT(*) AS n_flights,
       ROUND(SUM(b.invoice_amount),2) AS revenue
FROM reservations r JOIN billing b ON r.reservation_id=b.reservation_id
GROUP BY month ORDER BY month LIMIT 6;
""", conn))

8.4 Generate a working dataset

Same discipline as Project 6: a seeded synthetic generator, so the whole project is runnable and reproducible without any real customer data.

python — synthetic private-aviation data generator
import numpy as np, pandas as pd
rng = np.random.default_rng(11)
N_CUST, N_RES = 500, 2500

airports = ["TEB","VNY","APF","HPN","MIA","ASE"]   # private-aviation FBO codes
tiers    = ["Standard","Premium","Elite"]
acft     = ["Turboprop","Light Jet","Midsize Jet","Heavy Jet"]

start, end = pd.Timestamp("2025-01-01"), pd.Timestamp("2026-01-01")
def rand_dates(n):
    return start + pd.to_timedelta(rng.integers(0, (end-start).days, n), unit="D")

customers = pd.DataFrame({
    "customer_id": range(1, N_CUST+1),
    "membership_tier": rng.choice(tiers, N_CUST, p=[0.5, 0.35, 0.15]),
    "home_airport": rng.choice(airports, N_CUST),
    "join_date": rand_dates(N_CUST),
})

reservations = pd.DataFrame({
    "reservation_id": range(1, N_RES+1),
    "customer_id": rng.choice(customers.customer_id, N_RES),
    "flight_date": np.sort(rand_dates(N_RES)),
    "departure_airport": rng.choice(airports, N_RES),
    "arrival_airport": rng.choice(airports, N_RES),
    "aircraft_type": rng.choice(acft, N_RES, p=[0.2, 0.35, 0.3, 0.15]),
    "flight_hours": np.round(rng.gamma(3, 0.7, N_RES), 1),
    "lead_time_days": rng.integers(0, 60, N_RES),
})
m = reservations.merge(customers, on="customer_id")
# Hypothesis: very last-minute bookings cancel/no-show more; Elite members,
# who book through a concierge, follow through more reliably.
logit = (-0.03*(m.lead_time_days - 20) - 0.4*(m.membership_tier == "Elite").astype(int)
         + rng.normal(0, 1.6, N_RES))
reservations["flight_outcome"] = pd.cut(logit, bins=[-np.inf,-0.4,0.5,np.inf],
                                         labels=["Completed","No-Show","Cancelled"])

billing = pd.DataFrame({"invoice_id": range(1, N_RES+1), "reservation_id": reservations.reservation_id,
                         "invoice_amount": np.round(reservations.flight_hours * rng.uniform(2200, 5200, N_RES), 2)})
disp_p = 0.12 + rng.normal(0, 0.01, N_RES); u = rng.random(N_RES)
billing["payment_status"] = np.where(u < disp_p, "Disputed",
                              np.where(u < disp_p+0.22, "Pending", "Paid"))
billing["paid_amount"]   = np.where(billing.payment_status == "Disputed", np.nan,
                                     billing.invoice_amount * rng.uniform(0.85, 1.0, N_RES))
billing["payment_days"]  = np.where(billing.payment_status == "Paid",
                                     rng.integers(2, 25, N_RES).astype(float), np.nan)
print(customers.shape, reservations.shape, billing.shape)

8.5 EDA: the same bug, a different table

python — merge, audit missingness, and check the timeline
df = (reservations.merge(customers, on="customer_id")
                  .merge(billing, on="reservation_id")
                  .sort_values("flight_date").reset_index(drop=True))
print(df.shape)

print(df.groupby("payment_status")["paid_amount"].apply(lambda x: x.isna().sum()))
print(df.groupby("payment_status")["payment_days"].apply(lambda x: x.isna().sum()))
# paid_amount null ONLY for Disputed -- MNAR, same reasoning as Project 6:
# a disputed invoice was never paid, so null secretly means 0.

impossible = (df.flight_date < df.join_date).mean()
print(f"flights before the customer joined: {impossible:.1%}")
# ~49% here -- the exact same class of bug as Project 6's registration
# date issue, because join_date was generated independently of flight_date.
# Different industry, identical root cause: two dates that SHOULD have a
# one-directional relationship, generated without enforcing it.
⚠️ This is the most transferable lesson in the whole course

Any dataset with a "when did the relationship start" date (registration, sign-up, join, onboarding) and a "when did this event happen" date (visit, flight, order, claim) is at risk of this exact bug. The check is always the same one line: (event_date < relationship_start_date).mean(). Run it on every dataset you're handed, in any industry, before you trust a single date-derived feature.

8.6 Outlier detection

python — IQR outliers on invoice_amount, flight_hours, payment_days
for col in ["invoice_amount", "flight_hours", "payment_days"]:
    q1, q3 = df[col].quantile([0.25, 0.75])
    iqr = q3 - q1
    lo, hi = q1 - 1.5*iqr, q3 + 1.5*iqr
    n_out = ((df[col] < lo) | (df[col] > hi)).sum()
    print(f"{col}: {n_out} outliers, bounds=[{lo:.1f}, {hi:.1f}]")
# Every flag is high-side again -- a long heavy-jet repositioning flight
# or a slow-paying corporate account isn't an error, it's the tail of a
# real-world process. Investigate before deleting, exactly as in Project 6.

8.7 Feature engineering, with reasoning

python — build the feature set
# Hypothesis: a customer's own flight history predicts how their NEXT
# flight will go -- frequent flyers behave differently from one-time bookers.
agg = df.groupby("customer_id").agg(cust_flight_freq=("reservation_id","count"),
                                     cust_avg_flight_hrs=("flight_hours","mean"))
df = df.merge(agg, on="customer_id")

# Hypothesis: time-of-flight matters (weekend leisure trips vs weekday
# business trips behave differently).
df["flight_month"]   = df.flight_date.dt.month
df["flight_quarter"] = df.flight_date.dt.quarter
df["flight_dow"]      = df.flight_date.dt.dayofweek
df["is_weekend_flight"] = (df.flight_dow >= 5).astype(int)

# Hypothesis: tenure changes behaviour. Left UNCLIPPED on purpose --
# Project 9 section 9.6 shows exactly what this costs in monitoring.
df["days_since_join"] = (df.flight_date - df.join_date).dt.days

print(df[["cust_flight_freq","cust_avg_flight_hrs","flight_month",
          "is_weekend_flight","days_since_join"]].describe().round(1))
✈️ Real-World Analogy

lead_time_days here plays the same role days_since_registration played for the hospital — a single number standing in for "how much is known about this booking in advance." A 2-day-notice charter and a 45-day-planned trip are different events wearing the same row shape; the feature is what lets a model tell them apart without you hand-writing a rule for every possible lead time.

✅ Check Yourself

Both Project 6 and Project 8 find a timeline bug affecting roughly half the rows. What does that tell you?
The same generative pattern (a relationship-start date drawn independently of an event date) produces the same kind of bug regardless of industry — which is exactly why the one-line timeline check in 8.5 is worth running on every dataset you ever touch.
Why engineer cust_flight_freq before training a model, instead of letting the model see raw individual reservation rows only?
Row-level data can't carry group-level patterns on its own. Aggregating to the customer level and merging the result back onto every row is how you give a row-based model access to history it otherwise can't see.
