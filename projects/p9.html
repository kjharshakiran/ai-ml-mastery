9.1 Recap: rebuild the modeling dataset

Paste Project 8's full generator (sections 8.4 + 8.7) if running this page fresh. Condensed here, with the leakage fix applied — exactly as Project 7 did for the hospital project:

python — rebuild df, train, test (see Project 8 for full derivation)
import numpy as np, pandas as pd
rng = np.random.default_rng(11)
N_CUST, N_RES = 500, 2500
airports=["TEB","VNY","APF","HPN","MIA","ASE"]; tiers=["Standard","Premium","Elite"]
acft=["Turboprop","Light Jet","Midsize Jet","Heavy Jet"]
start,end=pd.Timestamp("2025-01-01"),pd.Timestamp("2026-01-01")
rd=lambda n: start+pd.to_timedelta(rng.integers(0,(end-start).days,n),unit="D")
customers=pd.DataFrame({"customer_id":range(1,N_CUST+1),
  "membership_tier":rng.choice(tiers,N_CUST,p=[0.5,0.35,0.15]),
  "home_airport":rng.choice(airports,N_CUST),"join_date":rd(N_CUST)})
reservations=pd.DataFrame({"reservation_id":range(1,N_RES+1),
  "customer_id":rng.choice(customers.customer_id,N_RES),"flight_date":np.sort(rd(N_RES)),
  "departure_airport":rng.choice(airports,N_RES),"arrival_airport":rng.choice(airports,N_RES),
  "aircraft_type":rng.choice(acft,N_RES,p=[0.2,0.35,0.3,0.15]),
  "flight_hours":np.round(rng.gamma(3,0.7,N_RES),1),"lead_time_days":rng.integers(0,60,N_RES)})
m=reservations.merge(customers,on="customer_id")
logit=-0.03*(m.lead_time_days-20)-0.4*(m.membership_tier=="Elite").astype(int)+rng.normal(0,1.6,N_RES)
reservations["flight_outcome"]=pd.cut(logit,bins=[-np.inf,-0.4,0.5,np.inf],labels=["Completed","No-Show","Cancelled"])
billing=pd.DataFrame({"invoice_id":range(1,N_RES+1),"reservation_id":reservations.reservation_id,
  "invoice_amount":np.round(reservations.flight_hours*rng.uniform(2200,5200,N_RES),2)})
disp_p=0.12+rng.normal(0,0.01,N_RES); u=rng.random(N_RES)
billing["payment_status"]=np.where(u<disp_p,"Disputed",np.where(u<disp_p+0.22,"Pending","Paid"))
billing["paid_amount"]=np.where(billing.payment_status=="Disputed",np.nan,
  billing.invoice_amount*rng.uniform(0.85,1.0,N_RES))

df=reservations.merge(customers,on="customer_id").merge(billing,on="reservation_id").sort_values("flight_date").reset_index(drop=True)
df["days_since_join"]=(df.flight_date-df.join_date).dt.days   # unclipped on purpose -- see 9.6
df["flight_month"]=df.flight_date.dt.month; df["flight_quarter"]=df.flight_date.dt.quarter
df["flight_dow"]=df.flight_date.dt.dayofweek; df["is_weekend_flight"]=(df.flight_dow>=5).astype(int)

split=int(len(df)*0.8); train,test=df.iloc[:split].copy(),df.iloc[split:].copy()
agg=train.groupby("customer_id").agg(cust_flight_freq=("reservation_id","count"),
                                      cust_avg_flight_hrs=("flight_hours","mean"))
for part in (train,test):
    part["cust_flight_freq"]=part.customer_id.map(agg.cust_flight_freq)
    part["cust_avg_flight_hrs"]=part.customer_id.map(agg.cust_avg_flight_hrs)
print(len(train), len(test))

9.2 Train both models

Same choice of algorithms as Project 7, for the same reasons: Random Forest for the operational-risk target, Gradient Boosting for the revenue target.

python — Random Forest for flight_outcome
from sklearn.pipeline import Pipeline
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.ensemble import RandomForestClassifier, GradientBoostingClassifier
from sklearn.metrics import accuracy_score, f1_score, classification_report

FLIGHT_FEATURES = ["membership_tier","home_airport","departure_airport","aircraft_type",
                    "lead_time_days","days_since_join","cust_flight_freq","cust_avg_flight_hrs",
                    "flight_month","flight_quarter","flight_dow","is_weekend_flight"]
cat = [f for f in FLIGHT_FEATURES if not pd.api.types.is_numeric_dtype(df[f])]
num = [f for f in FLIGHT_FEATURES if pd.api.types.is_numeric_dtype(df[f])]
pre = ColumnTransformer([("ohe", OneHotEncoder(handle_unknown="ignore"), cat),
                          ("sc",  StandardScaler(), num)])
flight_model = Pipeline([("pre", pre), ("clf", RandomForestClassifier(
    n_estimators=200, min_samples_leaf=5, class_weight="balanced_subsample", random_state=42))])
flight_model.fit(train[FLIGHT_FEATURES], train.flight_outcome)

print("train acc:", round(accuracy_score(train.flight_outcome, flight_model.predict(train[FLIGHT_FEATURES])), 3))
print("test acc:", round(accuracy_score(test.flight_outcome, flight_model.predict(test[FLIGHT_FEATURES])), 3))
# train ~0.88, test ~0.45 -- the same overfitting story as Project 7's
# risk model, on a completely different target and industry.
python — Gradient Boosting for payment_status
BILL_FEATURES = ["membership_tier","aircraft_type","flight_outcome","invoice_amount",
                  "lead_time_days","days_since_join","cust_flight_freq",
                  "flight_month","flight_quarter","is_weekend_flight"]
catb = [f for f in BILL_FEATURES if not pd.api.types.is_numeric_dtype(df[f])]
numb = [f for f in BILL_FEATURES if pd.api.types.is_numeric_dtype(df[f])]
preb = ColumnTransformer([("ohe", OneHotEncoder(handle_unknown="ignore"), catb),
                           ("sc",  StandardScaler(), numb)])
bill_model = Pipeline([("pre", preb), ("clf", GradientBoostingClassifier(
    n_estimators=150, max_depth=4, subsample=0.8, random_state=42))])
bill_model.fit(train[BILL_FEATURES], train.payment_status)
preds = bill_model.predict(test[BILL_FEATURES])
print(classification_report(test.payment_status, preds, digits=3))
# Typical result: train ~0.88, test ~0.62 accuracy -- but the per-class
# breakdown tells the real story: Disputed recall ~0.22, Pending recall
# ~0.10. The model defaults to predicting "Paid" because that's the
# majority class -- exactly Project 7's claim-model finding, again.
⚠️ 61.8% accuracy is hiding a model that's nearly useless for its actual job

If "catch disputes before they happen" is the business goal, the metric that matters is Disputed recall (~22%), not overall accuracy. A model that's "right" 62% of the time mostly by calling everything "Paid" gives finance a false sense of coverage. This is the single most common way ML projects quietly fail in production: optimizing and reporting the metric that looks good, not the one the business actually needs.

9.3 Fairness: a real, severe gap this time

Run the same group-recall check Project 7 ran — by membership tier, by home airport, and by aircraft type for the billing model:

python — fairness across customer and aircraft groups
def group_recall(target, preds, truth, group_col, frame):
    out = {}
    for g in frame.loc[truth.index, group_col].unique():
        idx = frame.loc[truth.index, group_col] == g
        t, p = truth[idx], preds[idx]
        if (t == target).sum() == 0: continue
        out[g] = round(float(((p == target) & (t == target)).sum() / (t == target).sum()), 3)
    return out

fpreds = flight_model.predict(test[FLIGHT_FEATURES])
print("Cancelled recall by membership_tier:",
      group_recall("Cancelled", fpreds, test.flight_outcome, "membership_tier", df))
# Standard 0.386, Elite 0.185, Premium 0.452 -- Elite members who cancel
# are caught LESS than half as often as Standard members who cancel.

bpreds = bill_model.predict(test[BILL_FEATURES])
print("Disputed recall by aircraft_type:",
      group_recall("Disputed", bpreds, test.payment_status, "aircraft_type", df))
# Heavy Jet: 0.0 -- the model NEVER catches a disputed Heavy Jet invoice
# in this test set. Zero is not a rounding error; it's a hard miss on
# the highest-value bookings in the entire business.
🛫 Real-World Analogy

Imagine an airport security line with four lanes, and one of them — the one VIPs use — has a metal detector that's quietly never once gone off, for anyone, ever. Looking at the other three lanes' detection rates would never tell you that. You only find it by checking every lane separately, which is exactly what group_recall does instead of reporting one company-wide number.

🔑 A 0% recall on your highest-value segment is a launch blocker, not a footnote

Heavy Jet invoices are almost certainly the largest dollar amounts in this business. A model that never flags a single one of their disputes isn't a minor fairness nuance — it's a finance team flying blind on its biggest exposure. Compare this to Project 7's hospital fairness gap, where every group's recall was low: there, the honest read was "no real signal anywhere." Here, some groups (Standard, Premium) have meaningfully higher recall than others (Elite, Heavy Jet) — that's a targeted weakness, and it's the kind of finding that should block a launch until it's understood, not just logged and shipped.

9.5 Monitoring: PSI catches the bug again

python — PSI on days_since_join
def psi(ref, curr, bins=10):
    b = np.linspace(min(ref.min(), curr.min()), max(ref.max(), curr.max()), bins+1)
    b[0] -= 1e-6; b[-1] += 1e-6
    rp = (pd.cut(ref, bins=b).value_counts(sort=False) / len(ref)).clip(lower=1e-6)
    cp = (pd.cut(curr, bins=b).value_counts(sort=False) / len(curr)).clip(lower=1e-6)
    return float(((cp - rp) * np.log(cp / rp)).sum())

score = psi(train.days_since_join, test.days_since_join)
print(f"PSI(days_since_join) = {score:.2f}")
print("ref mean:", round(train.days_since_join.mean(),1), " curr mean:", round(test.days_since_join.mean(),1))
# PSI ~5.5, ref mean ~ -34, curr mean ~ +144 -- the SAME false alarm
# as Project 7's days_since_registration, for the SAME root cause
# (Project 8 section 8.5). Two industries, one bug, one fix:
# add .clip(lower=0) at the source instead of retraining a fine model.
