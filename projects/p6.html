Hospital Risk Intelligence I — From Raw Tables to a Modeling Dataset

🔴 Difficulty: Advanced🎯 Mimics a real hospital analytics team's first two weeks🧰 SQL · EDA · Feature Engineering

What you'll build

  • A realistic three-table hospital schema (patients, visits, billing) and the SQL to interrogate it like an analyst would, before a single model is trained.
  • A full EDA pass that finds two genuine data-quality bugs hiding in the tables — the same two a real capstone project shipped with.
  • A defensible missing-value strategy that reasons about why a value is missing (MCAR / MAR / MNAR), not just fills it in.
  • An engineered feature set — patient history, provider behaviour, time-of-visit — built the way a production feature store would build it.
  • A time-based train/test split, and the reasoning for why a hospital (or any company shipping a model into the future) never uses a random shuffle.
The Big Question
A hospital hands you three raw tables and one ask — "tell us which visits are high-risk and which claims will get rejected, before they happen." Where do you even start, and how do you know your starting point isn't already lying to you?

6.1 The brief

This two-part project (Project 6 + Project 7) rebuilds — concept by concept, with real numbers — an actual production-style system: Hospital Operations & Revenue Risk Intelligence. A hospital group wants two predictions made automatically, the moment a visit and its bill are recorded:

  • Visit risk (risk_score: Low / Medium / High) — so clinical staff can prioritise attention.
  • Claim outcome (claim_status: Paid / Pending / Rejected) — so the revenue team can chase the claims most likely to be rejected, before they're rejected.

Project 6 covers the part that takes 70% of real project time and gets none of the glory: turning three raw tables into one trustworthy modeling dataset. Project 7 takes that dataset to trained models, a live API, and a monitoring loop. This is, in miniature, exactly what a data team does in their first sprint on any tabular ML problem — be it hospital claims, e-commerce churn, or (Projects 8–9) private-jet reservations.

🧒 Explain Like I'm 10

Imagine three notebooks on a hospital reception desk: one lists patients (who they are), one lists visits (who came in, when, why), and one lists bills (how much, did the insurance pay). Before you can teach a computer to guess "is this visit risky?" you first have to staple the right pages from all three notebooks together for every single visit — and check that nobody wrote something impossible, like a bill dated before the patient ever walked in.

6.2 The data model: three tables, one patient journey

Every row in visits is one hospital visit. It points at exactly one row in patients (who) via patient_id, and exactly one row in billing (the money) via visit_id. This is a textbook one-to-many relationship (Week 5): one patient, many visits; one visit, one bill.

6.3 SQL first — ask the business questions before you open Python

A production data team never opens a notebook first. They open SQL, because the database already has the answers to the questions a hospital administrator actually asks: which department sees the most volume, which insurer rejects the most claims, who are our highest-billed patients? This is Week 5's relational model, put to work.

python — build an in-memory SQL database
import sqlite3, pandas as pd

# In production this would be Postgres/Snowflake; sqlite3 (Python's
# built-in) is the same SQL for learning purposes, no server needed.
conn = sqlite3.connect(":memory:")

# `patients`, `visits`, `billing` are the three DataFrames we'll build
# in section 6.4 below. Loading them as real SQL tables lets us write
# real SQL against them -- copy this cell AFTER running 6.4 once.
patients.to_sql("patients", conn, index=False)
visits.to_sql("visits", conn, index=False)
billing.to_sql("billing", conn, index=False)
print("3 tables loaded into SQL.")

Question 1 — where's the volume, and what does it cost? A simple JOIN + GROUP BY, the bread and butter of analytics SQL:

sql — visits and average bill by department
q1 = """
SELECT department, COUNT(*) AS n_visits, ROUND(AVG(b.billed_amount),2) AS avg_bill
FROM visits v JOIN billing b ON v.visit_id = b.visit_id
GROUP BY department ORDER BY n_visits DESC;
"""
print(pd.read_sql(q1, conn))
# Orthopedics / ICU / General / ER / Cardiology / Neurology all land
# within a few hundred visits of each other -- no department dominates,
# which matters later: a model can't just learn "always predict the
# busiest department's typical outcome."

Question 2 — which insurer is riskiest to bill? A CASE WHEN inside an aggregate turns a row-level flag into a rate — one of the most useful SQL patterns there is:

sql — rejection rate by insurer
q2 = """
SELECT insurance_provider,
       ROUND(100.0 * SUM(CASE WHEN claim_status='Rejected' THEN 1 ELSE 0 END)
             / COUNT(*), 1) AS rejection_pct
FROM visits v
JOIN billing b ON v.visit_id = b.visit_id
JOIN patients p ON v.patient_id = p.patient_id
GROUP BY insurance_provider ORDER BY rejection_pct DESC;
"""
print(pd.read_sql(q2, conn))
# Typical output: every insurer sits within a few points of ~15%.
# That's the FIRST clue for Project 7 -- if every insurer rejects at
# roughly the same rate, "insurance_provider" alone won't be a strong
# predictor of rejection. Good models need this kind of honest signal
# check before you ever fit one.
🔑 SQL answers "what happened." ML answers "what's next."

Notice neither query above involved any machine learning — they're pure aggregation, and they already told us something a model will need to know (insurers reject at similar rates, so rejection isn't simply "blame the insurer"). Always exhaust the SQL questions first. It's faster, it's exact, and it tells you what a model even has a chance of learning.

Question 3 — who are our highest-billed patients, and how does revenue trend month to month? Two more patterns you'll reuse constantly: a multi-table JOIN with ORDER BY … LIMIT, and SQLite's date function for a monthly rollup.

sql — top patients by spend, and revenue by month
q3 = """
SELECT p.patient_id, COUNT(*) AS n_visits, ROUND(SUM(b.billed_amount),2) AS total_billed
FROM visits v JOIN billing b ON v.visit_id=b.visit_id
              JOIN patients p ON v.patient_id=p.patient_id
GROUP BY p.patient_id ORDER BY total_billed DESC LIMIT 5;
"""
print(pd.read_sql(q3, conn))

q4 = """
SELECT strftime('%Y-%m', visit_date) AS month, COUNT(*) AS n_visits,
       ROUND(SUM(b.billed_amount),2) AS revenue
FROM visits v JOIN billing b ON v.visit_id=b.visit_id
GROUP BY month ORDER BY month LIMIT 6;
"""
print(pd.read_sql(q4, conn))
# This monthly view is exactly what later powers the time-based
# train/test split in 6.8 -- SQL already shows the data has a calendar
# axis you must respect, not shuffle away.

6.4 Generate a working dataset

The real version of this project runs on hospital records that can't be published. So — exactly like a course should — we'll generate a seeded synthetic dataset with the same shape, the same realistic messiness, and (because the seed is fixed) the same bugs. Everything from here on runs on data you can reproduce yourself, in this page, right now.

python — synthetic hospital data generator
import numpy as np
import pandas as pd

rng = np.random.default_rng(7)
N_PAT, N_VIS = 600, 3000

cities    = ["Hyderabad","Pune","Bangalore","Mumbai","Delhi","Chennai"]
insurers  = ["MediCareX","CareOne","HealthPlus","SecureLife"]
depts     = ["General","ER","Neurology","Orthopedics","Cardiology","ICU"]
vtypes    = ["ER","OPD","ICU"]

start, end = pd.Timestamp("2025-01-01"), pd.Timestamp("2026-01-01")
def rand_dates(n):
    return start + pd.to_timedelta(rng.integers(0, (end-start).days, n), unit="D")

patients = pd.DataFrame({
    "patient_id": range(1, N_PAT+1),
    "age": rng.integers(1, 90, N_PAT),
    "gender": rng.choice(["M","F"], N_PAT),
    "city": rng.choice(cities, N_PAT),
    "insurance_provider": rng.choice(insurers, N_PAT),
    "chronic_flag": rng.integers(0, 2, N_PAT),
    "registration_date": rand_dates(N_PAT),
})

visits = pd.DataFrame({
    "visit_id": range(1, N_VIS+1),
    "patient_id": rng.choice(patients.patient_id, N_VIS),
    "visit_date": np.sort(rand_dates(N_VIS)),
    "department": rng.choice(depts, N_VIS),
    "visit_type": rng.choice(vtypes, N_VIS),
    "length_of_stay_hours": np.round(rng.gamma(4, 5, N_VIS), 1),
    "doctor_id": rng.integers(1, 40, N_VIS),
})
joined = visits.merge(patients, on="patient_id")
risk_logit = (0.01*(joined.age - 45) + 0.3*joined.chronic_flag
              + rng.normal(0, 1.5, N_VIS))
visits["risk_score"] = pd.cut(risk_logit, bins=[-np.inf,-0.3,0.6,np.inf],
                               labels=["Low","Medium","High"])

billing = pd.DataFrame({"bill_id": range(1, N_VIS+1), "visit_id": visits.visit_id,
                         "billed_amount": np.round(rng.gamma(6, 3500, N_VIS), 2)})
rej_p = 0.15 + rng.normal(0, 0.01, N_VIS)
u = rng.random(N_VIS)
billing["claim_status"] = np.where(u < rej_p, "Rejected",
                            np.where(u < rej_p+0.25, "Pending", "Paid"))
billing["approved_amount"] = np.where(billing.claim_status == "Rejected", np.nan,
                                       billing.billed_amount * rng.uniform(0.7, 1.0, N_VIS))
billing["payment_days"] = np.where(billing.claim_status == "Paid",
                                    rng.integers(3, 30, N_VIS).astype(float), np.nan)

print(patients.shape, visits.shape, billing.shape)
# (600, 7) (3000, 7) (3000, 5) -- three independent tables, ready to join.
🎲 Real-World Analogy

A seed (default_rng(7)) is like a recipe number, not a dice roll. Anyone who runs this exact cell gets the exact same "random" hospital, down to the last decimal. That's why companies seed their synthetic test fixtures and why this lesson can promise "you'll see a 49% something-is-wrong rate" several paragraphs from now — it isn't a coincidence, it's the same seed producing the same data, every time.

6.5 EDA: missing values, and reasoning about why

Week 8 taught you to check .isna().sum(). A junior analyst stops there. A senior one asks why a value is missing, because the fix depends entirely on the mechanism:

  • MCAR (missing completely at random) — a sensor glitch, no pattern. Safe to drop or impute simply.
  • MAR (missing at random, but predictable from other columns) — e.g. older patients skip an optional field more often.
  • MNAR (missing not at random) — the missingness is the information. This is what we have here.
python — merge the tables, then audit missingness by reason
df = (visits.merge(patients, on="patient_id")
            .merge(billing, on="visit_id")
            .sort_values("visit_date").reset_index(drop=True))
print(df.shape)   # (3000, 19) -- a clean inner join, no orphan rows

print(df[["approved_amount","payment_days"]].isna().sum())

# THE question: does the null line up with WHY it should be null?
print(df.groupby("claim_status")["approved_amount"].apply(lambda x: x.isna().sum()))
print(df.groupby("claim_status")["payment_days"].apply(lambda x: x.isna().sum()))
# approved_amount is null ONLY for Rejected claims -- a rejected claim
# was never approved, so null here secretly means "zero". That's MNAR:
# the fact that it's missing tells you the value would have been 0.
# payment_days is null for Pending/Rejected -- nothing has been paid
# yet, so there ARE no days-to-pay. Also MNAR, also expected.
⚠️ A bug this exact dataset really shipped with

Run the cell below. In the real capstone project this course is based on, 48.6% of visits had a visit_date earlier than the patient's own registration_date — a patient "visiting" a hospital before they'd registered with it. The synthetic generator above reproduces the same bug on purpose (registration dates are drawn independently of visit dates), because spotting it is the whole lesson: EDA's job is to find exactly this kind of impossible row before it quietly poisons a feature in section 6.7.

python — the timeline sanity check most teams skip
impossible = (df.visit_date < df.registration_date).mean()
print(f"visits before the patient registered: {impossible:.1%}")
# ~49% here. In production this is the single highest-value EDA check
# you can run on any dataset with two dates: does the story they tell,
# told in order, even make sense?

6.6 Outlier detection — a question, not a verdict

Week 8's IQR rule, applied to the three numeric columns that matter most for risk and revenue:

\[ \text{outlier if } x < Q_1 - 1.5\,\text{IQR} \ \text{ or } \ x > Q_3 + 1.5\,\text{IQR} \]

python — IQR outliers on billed_amount, LOS, payment_days
for col in ["billed_amount", "length_of_stay_hours", "payment_days"]:
    q1, q3 = df[col].quantile([0.25, 0.75])
    iqr = q3 - q1
    lo, hi = q1 - 1.5*iqr, q3 + 1.5*iqr
    n_out = ((df[col] < lo) | (df[col] > hi)).sum()
    print(f"{col}: {n_out} outliers, bounds=[{lo:.1f}, {hi:.1f}]")

# Winsorise (cap, don't delete) the longest stays at the 99th percentile --
# keeps the shape of the distribution, removes the extreme tail's leverage
# on a model, and throws away zero rows.
cap = df["length_of_stay_hours"].quantile(0.99)
df["los_winsorized"] = df["length_of_stay_hours"].clip(upper=cap)

Every flagged value here is on the high side — long stays, big bills, slow payments — which is exactly what you'd expect in a hospital: nothing is naturally negative, so the long tail is real ICU stays and large procedures, not data corruption. That's a judgement call EDA forces you to make, every time.

6.7 Feature engineering, with reasoning

A feature isn't "a column" — it's a claim about what predicts the target. Each one below is engineered because of a specific hypothesis a hospital analyst would actually have:

python — build the feature set
# Hypothesis: patients with a longer visit history have an established
# pattern -- frequency and average stay say something a single visit can't.
agg = df.groupby("patient_id").agg(
    patient_visit_freq=("visit_id", "count"),
    patient_avg_los=("length_of_stay_hours", "mean"),
)
df = df.merge(agg, on="patient_id")

# Hypothesis: time-of-visit matters (weekend staffing, month-end billing
# pushes, etc.) -- cheap to compute, often surprisingly predictive.
df["visit_month"]      = df.visit_date.dt.month
df["visit_quarter"]    = df.visit_date.dt.quarter
df["visit_dayofweek"]  = df.visit_date.dt.dayofweek
df["is_weekend_visit"] = (df.visit_dayofweek >= 5).astype(int)

# Hypothesis: how long someone has been a patient changes their risk
# profile. NOTE: we deliberately do NOT clip this at zero yet -- Project 7
# section 7.6 shows you exactly what that omission costs you in production.
df["days_since_registration"] = (df.visit_date - df.registration_date).dt.days

print(df[["patient_visit_freq","patient_avg_los","visit_month",
          "is_weekend_visit","days_since_registration"]].describe().round(1))
⚠️ Leakage lives in aggregate features

A feature like "this insurer's overall rejection rate" is enormously useful — and enormously dangerous if computed on the whole dataset before splitting. Computing it on data that includes the future (relative to a given training cutoff) lets the model quietly see outcomes it shouldn't know yet. Project 7 computes this feature, and explicitly recomputes it on the training split only — note the warning baked into the real project's code: # NOTE: this is computed on the full dataset here for EDA only.

6.8 The time-based split — why production never shuffles

train_test_split(shuffle=True) (Week 13) is the right call when rows are independent and unordered. A hospital's visits are not — they have a calendar, and the whole point of the model is to predict the future from the past. A random shuffle would let the model train on tomorrow's pattern to predict yesterday: a leak that makes your validation score lie to you.

python — split by time, not by chance
df = df.sort_values("visit_date").reset_index(drop=True)
split = int(len(df) * 0.8)
train, test = df.iloc[:split], df.iloc[split:]

print(f"train: {len(train)} rows, {train.visit_date.min().date()} -> {train.visit_date.max().date()}")
print(f"test:  {len(test)} rows,  {test.visit_date.min().date()} -> {test.visit_date.max().date()}")
# Every feature that aggregates across patients/insurers/departments
# (section 6.7) should, in a real production build, be RE-fit on `train`
# only. We carry the modeling dataset into Project 7 exactly this way.

✅ Check Yourself

approved_amount is null only when claim_status == "Rejected". What kind of missingness is this?
The null lines up perfectly with a business reason (rejection), not chance. That's MNAR — and it tells you the correct fix is to fill with 0, not a mean or median.
Why split a hospital dataset by time (earliest 80% / latest 20%) instead of a random shuffle?
A random shuffle interleaves future and past rows into both train and test, leaking information about the future into training. A time-based split mirrors exactly how the model will be used the day it ships.
What does the IQR outlier check on billed_amount, length_of_stay_hours, and payment_days reveal in this dataset?
All three columns are naturally bounded at zero, so the IQR rule only ever flags the high tail — and that tail is exactly where the real signal (ICU stays, big procedures, slow claims) tends to live. Investigate, don't auto-delete.
